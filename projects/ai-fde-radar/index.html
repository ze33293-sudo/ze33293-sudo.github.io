1. 项目概览与核心价值

基于 Horizon 开源框架，我面向个人 AI 学习与求职需求设计六栏简报，制定来源分层、相关性筛选、去重和缺栏规则。工作流串联信息采集、模型摘要、飞书卡片生成与定时发送，已持续稳定运行。

产品重点是让读者知道内容为何入选、能否追溯来源，以及哪些栏目暂时没有可靠更新。预检模式用于在正式发送前检查来源和栏目覆盖，其运行不调用模型、不发送飞书消息。

2. 项目背景和机会判断

AI 信息增长速度快，普通 RSS 阅读器解决了聚合问题，却没有解决“哪些内容与我的岗位相关”。手动浏览又会在多个来源之间切换，容易重复阅读，也难以长期维持固定结构。

我将信息需求整理为五个外部信息栏目，加上一栏当日行动建议，共六栏。前五栏分别覆盖行业趋势、企业落地案例、产品方法与踩坑、小白技术翻译、中国与求职信号，最后一栏为“今天就能用”。

3. 目标用户、使用场景与现有流程

首位用户是我本人，也可以扩展给需要持续跟踪 AI 应用和 FDE 岗位的人。主要场景是工作日上午在飞书查看一份结构稳定的中文简报，无需逐个打开几十个网站。

原流程依赖收藏夹、搜索和零散订阅。我将采集、筛选、摘要、排版、发送和历史去重组织为自动化工作流，并保留原始链接供核验；各阶段的运行状态分开记录。

4. 需求与优先级

P0：来源可追溯、摘要不脱离原文，敏感配置不进入公开产物。这两项决定简报能否被信任并持续运行。

P1：保持六栏结构、跨日去重，并能定位失败环节。运行中出现来源提取失败和重复告警后，我进一步明确：单栏没有可靠内容可以显示缺栏说明，同一计划运行的失败提醒应汇总。

P2：网页归档和更多分发渠道。先围绕个人每日接收与阅读简报的需求完善流程，再扩展触达方式。

5. 目标与验收标准

成功标准包括：五个外部信息栏目均经过可信来源校验；最后一栏基于当日内容生成行动建议；相同 URL 或高度相似事件不重复推送；缺栏不触发整期失败；预检模式不调用付费模型、不发送飞书、不发布页面。

运行指标包括抓取量、规则预筛选保留量、各栏候选覆盖、去重数量、模型调用次数、发送状态和失败原因。长期价值指标仍需进一步统计，例如每日阅读率、链接点击率和实际行动转化。

6. 我的职责与协作边界

我将信息需求拆成六栏内容标准，制定来源分层、筛选与去重规则；遇到来源提取失败和重复告警后，调整候选配额、缺栏处理及通知粒度，并负责工作流验收。

工程基础来源于 MIT 许可的开源项目 Horizon。Horizon 原作者完成了通用新闻采集、评分和多渠道分发框架；我完成的是面向个人 AI/FDE 情报需求的配置与产品改造。开源上游能力和我的改造范围在作品集中明确区分。

7. 调研、替代方案与范围取舍

我的选择标准是：能否按个人岗位需求筛选内容、能否跨日去重，以及后续需要维护多少通用采集工作。手动搜索和订阅聚合之后，我仍需筛选内容、整理栏目；完全从零实现则需要同时承担通用采集器的维护。

最终选择 Horizon 作为通用底座，把时间集中在内容标准、来源质量、中文摘要、飞书交付和安全运行上。第一阶段也没有追求覆盖所有媒体，而是先建立官方来源、可信社区和补充来源的分层机制。

8. 方案与使用流程

GitHub Actions 的定时配置为北京时间 09:15。流程先抓取来源，再执行 URL 清洗、来源分级、时间窗口和关键词筛选及跨日去重，并进入摘要生成和飞书推送。

首次发现窗口约为 30 小时，用于覆盖时区差异和更新延迟；某栏缺少候选时，可以在限定来源中回溯约 7 天。规则筛选后，再由 DeepSeek 按岗位相关性、信息密度和可行动性进行评分与中文摘要。

系统将结果组织为六栏飞书卡片，并将已见条目和当日发送标记持久化到 GitHub Pages 分支。正式发送前支持 preflight-only：主动清空模型与飞书凭据，只验证外部来源和内容覆盖，保证模型调用数与发送数均为零。

9. 三项关键决策及其权衡

第一，设置内容质量底线。

某栏没有可靠更新时直接展示占位说明，避免为了结构完整而填入低质量内容。代价是简报偶尔不满栏，但可信度更稳定。

第二，将来源预检与正式生成发送分开。

预检用于发现来源失效和栏目候选不足，不调用模型、不发送飞书消息；完整生成发送流程已持续运行，摘要质量、卡片呈现和重复发送问题应在正式流程中检查，不能由预检结果代替。

第三，持久化去重与发送状态，并设置并发互斥和有限重试。

这样可以降低工作流重复触发造成的重复推送；代价是必须处理状态损坏、恢复和跨分支同步问题。

10. AI、规则与人工分工

规则负责来源白名单、栏目映射、时间窗口、跨日去重、安全检查和流程状态。DeepSeek 负责相关性评分、压缩摘要和行动建议，模型不能绕过来源要求，也不能自行生成不存在的链接。

GitHub Actions 负责定时、环境安装、重试、状态持久化和产物发布；飞书 Webhook 负责最终触达。人工负责调整栏目标准、审核新来源、复盘误选内容与异常运行，并维护正式推送配置。

11. 数据与技术方案

来源包括 OpenAI、Microsoft、Google、NVIDIA、AWS 等官方内容，GitHub Release、Hacker News 及面向中国市场的补充信号源。来源按可靠性和栏目适配度分层，并为容易缺栏的类别预留候选名额。

当前配置使用 DeepSeek API 的 deepseek-v4-flash，采用较低温度和结构化输出约束。工作流运行于 Python 3.12 和 uv 环境，模型密钥与飞书 Webhook 存储在 GitHub Secrets 中。

12. 评测与案例复盘

一次云端预检抓取了 533 条候选，经规则预筛选保留 45 条，但“中国与求职信号”栏因三个招聘页面无法稳定提取而失败。该结果暴露出“每栏必须填满”会让局部来源问题拖垮整期任务。

调整来源、候选配额与缺栏策略后，早期云端预检记录为五个外部信息栏目 5/5 可用；该次预检在 AI 评分前停止，模型调用为 0、飞书发送为 0、Pages 发布跳过。另有历史记录显示阶段性全量测试 530 项通过，该数字不代表个人新增测试量或正式发送次数。

另一个 Bad Case 是同一计划运行中的多次尝试曾分别发出失败提醒。我将通知粒度从“每次尝试”改为“每次计划运行”，避免一次任务异常产生重复告警。

上述记录保留了来源采集、零调用预检及早期问题修复过程。目前完整摘要生成、卡片发送和定时推送流程已投入使用，并持续稳定运行。

13. 风险与异常处理

API 密钥和 Webhook 仅通过 Secrets 注入。公开产物发布前执行敏感信息扫描，避免凭据进入网页、日志和测试附件。预检模式主动移除相关环境变量，形成代码层面的零调用保证。

系统最多重试一次；内容结构或必需栏目出现不可恢复错误时停止发送。单栏无可靠内容时使用明确占位，不让模型自行补写。来源 URL、跳转目标和输出链接均接受安全校验。

14. 成果与验证范围

本阶段完成六栏标准、来源配置、去重与缺栏规则的改造；简报完整生成与发送流程已完成，并持续稳定运行。来源预检曾暴露招聘页面提取问题，调整后五个外部栏目候选覆盖为 5/5；阅读效率与具体运行指标尚未量化。

后续需量化发送成功率、阅读率、点击率和信息对决策的实际帮助。商业价值仍需进一步验证：相同机制可扩展为岗位情报、客户行业动态或售前线索简报，但需要针对组织权限和内容责任重新设计。

15. 项目复盘与下一步

招聘来源提取失败曾使单栏问题影响整期任务，我因此加入可靠内容缺失时的占位说明。重试产生重复失败提醒后，又将通知粒度调整为每次计划运行。两次变化都来自具体运行问题，后续持续关注来源变化、重复内容和异常通知。

下一阶段在持续运行的基础上，定期抽查摘要、来源、重复内容和卡片格式，积累发送成功率与阅读反馈，用实际记录检验缺栏策略与通知粒度的选择。
