1. 项目概览与核心价值

我将重复的英文 SRT 整理需求封装为 Skill，定义跨块合句、人名集中确认、句首英文字符大小写和标点标签处理，以及“一句一行”TXT 输出。它不承担完整语法纠错或翻译。

工作流将触发条件、处理顺序、人工确认和交付检查写成可复用规则。重点处理缩写被误断句、跨块残句和人名歧义，并要求保留源文件、检查输出完整性。

2. 项目背景和机会判断

英文字幕清洗看似简单，实际包含多种语义判断：一句话经常跨越多个字幕块；句点可能属于 Mr. 等缩写；人名可能被识别为普通单词；字幕中的标签、连字符和口语停顿也不能通过简单删除稳定处理。

重复手工操作的真正问题是规则无法复用，每次都要重新说明格式。Skill 将稳定要求写成长期工作流，让 Codex 在用户附加 SRT 文件时自动执行。

3. 目标用户、使用场景与现有流程

目标用户包括字幕整理、视频转写、课程笔记和英文内容编辑人员。

手工整理需要先删除时间码，再逐处修补断句和人名。新流程完整读取 SRT 后，先集中确认新增或歧义人名，再按原顺序合并跨块句子并清理格式，同时交付聊天文本和 TXT。把姓名确认放在清洗前，是为了避免一次错误判断被重复应用到整份字幕。

4. 需求与优先级

P0 是所有有效字幕文本保持原顺序和覆盖完整。

P0 是姓名不允许静默猜测或擅自删除。

P0 是源 SRT 文件保持不变。

P1 是跨字幕块重组完整句子，避免把每个字幕块误当一句话。

P1 是异常编码、损坏时间码和无法解析结构时停止交付。

P1 是已确认姓名映射能在同一对话中的后续文件复用。

P2 是批量质量统计、语言识别和图形界面。

5. 目标与验收标准

首版验收标准包括：

完整读取输入文件；

每个有效字幕文本均进入处理链；

输出顺序与原文一致；

每行只包含一个完整句子；

不保留字幕序号、时间码和表现标签；

新姓名或歧义姓名必须获得用户确认；

聊天输出与生成文件文本一致；

输出采用 UTF-8 BOM，便于 Windows 编辑器打开。

未来可以加入自动覆盖率、句界准确率、人工修改率和每千行处理时间等指标。当前没有足够标注样本支持准确率宣称。

6. 我的职责与协作边界

我将重复字幕整理拆成文件检查、人名集中确认、跨块合句和输出核对，明确歧义与异常时的停止条件，并整理成 Skill；Codex 按流程执行，用户先确认新出现或有歧义的人名。

Codex 负责根据 Skill 执行读取、重组、检查和文件生成；用户负责确认新的或存在歧义的人名。现阶段只有规范和实际输出证据，没有独立解析程序或大规模测试集。

7. 调研、替代方案与范围取舍

我比较了正则脚本、一次性提示词和 Skill 三种方式。正则适合删除时间码，却难以处理语义断句和人名；一次性提示词灵活，但规则容易遗漏；Skill 可以同时保留固定步骤和必要的人机确认。

首版聚焦英文 SRT 到纯文本，不承担翻译、内容摘要、说话人自动识别和时间轴重写，避免在一个工作流中混入过多目标。

8. 方案与使用流程

Skill 规定：附加 SRT 后先读取文件并检查字幕序号、时间范围和文本；编码或结构异常时停止该文件处理。这些是供 AI 执行的工作流要求，不是独立解析器提供的强制校验保证。

随后扫描所有新文件中的潜在人名，复用同一对话中已经确认的映射。新姓名、简称或存在多种解释的拼写进入一次集中确认。

确认人名后，按原顺序重组跨行、跨块句子，再处理句首英文字符的大小写、标点、标签和连字符。最终在对话中展示文本，另存为“原文件名_cleaned.txt”，并检查两份内容一致。

9. 三项关键决策及其权衡

第一，先重组句子，再清理标点。若提前删除标点和换行，会丢失判断边界的重要信号；代价是需要更多上下文分析。

第二，人名采用显式确认。系统不会凭发音或上下文强行音译，降低错误传播；代价是首次遇到新姓名时需要一次用户交互。

第三，异常时停止交付。面对乱码、损坏时间码或无法保证覆盖完整的文件，系统不生成看似完整的结果，避免静默丢句。

10. AI、规则与人工分工

AI 按 Skill 识别人名候选、重组跨块句子并修正语言格式。Skill 文档明确处理顺序、覆盖要求、禁止操作、停止条件和输出检查；规则执行质量仍需结合实际文件复核。

用户负责人名确认和原文含义的最终判断。文件工具只创建新的 cleaned.txt，不修改源 SRT。

11. 数据与技术方案

输入数据由 SRT 字幕块组成，每个块包含序号、时间码和一行或多行文本。处理状态包括当前输入文件、已确认人名映射、待确认姓名和输出路径。

姓名映射只在当前对话范围复用，不形成跨用户数据库。交付文件使用 UTF-8 BOM，并与聊天中的纯文本逐字核对。

12. 评测与案例复盘

当前证据包括 Skill 规范和一份已生成的英文字幕清洗结果。它证明工作流能够完成实际文件交付，但不足以支持大规模准确率结论。

需要覆盖的边界示例之一是将“Mr.”中的句点误当句末。此处用于说明断句风险，尚未形成独立标注和测试记录。

另一类边界是字幕块在“I wanted to”后结束，下一个块从“tell you...”开始。流程要求先按原顺序重组上下文，避免逐块清理留下残句。

人名短写也可能与普通单词重合。Skill 要求把歧义项集中交给用户确认；编码异常或疑似文本遗漏时停止处理。现有一份交付不能证明这些情况均已充分验证。

13. 风险与异常处理

源 SRT 保持不变，在授权目录生成新 TXT；Skill 不额外向外部渠道发布或转发字幕，人名映射仅在同一对话中复用。模型处理是否涉及服务端取决于实际运行环境，不将本地文件操作表述为全程离线。

本轮新姓名或歧义姓名未全部获得确认前，暂停清洗；文件编码或结构异常时停止对应文件处理。若目标文件写入失败，明确说明文件未生成，不把聊天文本当作文件交付成功。

14. 成果与验证范围

本阶段形成可复用 Skill 规范，并完成一份实际字幕文件的清洗交付。现有证据包括处理规则和输出样例，尚未建立独立解析程序或足以支持准确率结论的基准集。

已确认的人名映射可在同一对话的后续文件中复用，减少重复确认。句界质量、人工修改量和长字幕处理时间仍待通过标注样本测量。

15. 项目复盘与下一步

缩写误断句、跨字幕块残句和人名歧义是需要覆盖的边界情况。我将上下文重组、集中确认和输出一致性写为明确要求；现有实际文件交付不能证明每类边界情况都已充分测试。

下一阶段建立脱敏字幕基准集，标注姓名、跨块句界、缩写和异常结构，统计句界准确率与人工修改率，检验现有处理顺序、人名确认和交付检查规则。
