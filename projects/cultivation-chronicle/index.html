1. 项目概览与核心价值

围绕 AI 长期叙事中设定遗忘和人物状态被改写的问题，我设计了修真沙盒原型。玩家行为先由规则系统计算并写入事件账本，本地模型再依据事实包生成第一人称章节，玩家确认后保存为正式纪事。

项目的核心设计是“规则产生事实，AI负责叙事”。人物境界、关系、战斗结果和时间线由游戏系统决定，语言模型只能把既有事实写得更有文学表现力，不能擅自改写世界状态。

2. 项目背景和机会判断

大模型适合生成故事，却容易遗忘长期设定、改变人物关系或让角色获得不存在的能力。传统规则游戏保持一致性，但叙事反馈容易重复，难以体现玩家长期选择。

首版验证规则系统与模型叙事的分工：由规则与数据库记录发生了什么，由模型组织章节表达，并通过事实检查和玩家确认处理生成偏差。

3. 目标用户、使用场景与现有流程

目标用户是喜欢修真题材、长期养成、涌现故事和本地 AI 的单机玩家。

玩家创建世界后，可以探索区域、修炼、处理关系、加入宗门并参与战斗。阶段性事件被整理为章节草稿，玩家确认后才进入正式纪事；玩家也可以编辑草稿并导出 Markdown 或 TXT。

4. 需求与优先级

P0 是世界事实具有唯一可信来源。

P0 是相同种子和生成器版本能够复现初始世界。

P0 是 AI 不得改变战斗、关系、境界和事件因果。

P1 是长周期离线演化可恢复、可重复执行且不会重复结算。

P1 是旧事件能够被检索，为新章节提供长期记忆。

P1 是模型不可用时仍可继续游戏。

P2 是更丰富的内容、美术、语音和长期平衡。

5. 目标与验收标准

首版成功标准包括：同种子生成相同基础世界；所有状态变化均对应结构化事件；关键人物、敌人、地点和境界不能在章节中缺失；章节经玩家确认后才成为正式内容；向量索引损坏后可从 SQLite 重建；离线推进具备预算和幂等控制。

体验指标仍需用户测试，例如章节确认率、人工修改比例、事实冲突率、长期回流和不同流派的可玩性。

6. 我的职责与协作边界

我将游戏状态与叙事分层：规则决定境界、关系和战斗结果，模型只据事件写作；设计章节确认，并重点验收事实检查、重写与失败后的摘要回退。

当前为个人游戏原型。玩家确认决定哪些章节进入正式纪事，不等同于允许章节文本改写游戏状态；反向提案已有白名单校验接口，完整执行体验仍属待完善项。

7. 调研、替代方案与范围取舍

我比较了完全由模型担任游戏主持人、预写分支剧情和规则系统加模型叙事三种方式。模型主持自由度高，但难以保持长期一致；固定分支可靠，却难以覆盖涌现事件。

最终选择结构化事件账本。SQLite 保存事实和状态，LanceDB 只用于检索旧事件，语言模型只生成章节。首版优先打通可玩的规则循环和事实边界，暂缓多人、云同步和商业化内容生产。

8. 方案与使用流程

世界由种子生成区域、境界、宗门、功法和 42 名 NPC。玩家旅行、修炼或参与关系与宗门活动时，规则引擎验证条件、计算结果，并把随机决策和状态变化写入 SQLite。

战斗由 Phaser 场景执行，结果以结构化数据返回服务端校验。叙事服务从事件账本和历史检索中构造事实包，交给本地模型生成第一人称章节。

系统检查章节是否包含关键人物、敌人、地点、境界和事件结果。缺失时带原因重写一次；再次失败则生成确定性摘要。玩家审阅并确认后，章节才进入正式纪事。

9. 三项关键决策及其权衡

第一，以 SQLite 保存的状态和事件为准。

LanceDB 是便于查找旧事件的索引，损坏后可重建；章节则依据事件生成。这样既能用历史事件补充叙事，又不会让生成文本决定游戏事实；代价是玩法中的状态变化需要保存为结构化事件。

第二，章节实行“生成、检查、确认”。

玩家在章节正式保存前查看关键事实并修订文本，游戏状态始终以事件账本为准；代价是增加一次审阅确认。

第三，随机性进入事件账本。

这样能够复盘关键结果和离线推进；代价是事件设计与存储复杂度更高。

10. AI、规则与人工分工

规则系统负责世界生成、资源消耗、境界、关系、宗门、战斗和时间推进。SQLite 保存权威状态和事件，LanceDB负责检索相关旧事。

语言模型负责章节表达，玩家负责审阅并确认章节。已发生的境界、关系和胜负仍以规则状态为准；反向提案仅有受限校验能力，不把完整写回世界流程列为已交付成果。

11. 数据与技术方案

前端采用 React、TypeScript 和 Phaser，服务端采用 Node 与 SQLite。LanceDB 保存事件 Embedding，可在损坏或模型变化后根据 SQLite 重建。

本地 Ollama 使用 qwen3.5:9b 生成章节，qwen3-embedding:0.6b 检索历史；可选 CosyVoice 将已确认章节转换为语音。服务默认监听 127.0.0.1:4317。

离线演化采用时间预算、幂等键和关键事件冻结；独立试炼运行在隔离状态中，不写入正式世界。

12. 评测与案例复盘

现有测试覆盖种子复现、事件写入、关系与宗门状态、战斗结果校验、离线幂等、章节事实检查、模型降级和向量索引重建。

针对章节遗漏敌人、宗门或境界等信息，程序检查正文是否包含事件字段中的必要内容，缺失时要求重写一次；仍不合格则回退为事件摘要。当前主要使用字符串包含和少量规则，不能识别所有语义矛盾。

另一个风险是离线推进被重复调用，导致资源和事件重复结算。系统通过结算窗口和幂等标识拒绝重复处理。向量库异常时退回 SQLite 全文搜索或重建，不影响权威状态。

13. 风险与异常处理

游戏数据、模型调用和语音服务默认留在本机。服务只绑定回环地址，不要求云端账号。备份需要同时保留 SQLite 及其 WAL 状态，避免不完整复制。

Ollama 不可用时使用规则叙事；Embedding 不可用时退回 SQLite 检索；CosyVoice 不可用时保留文字和语音任务；LanceDB 损坏时从事件账本重建。降级会改变表现力，不会改变游戏事实。

14. 成果与验证范围

本阶段完成带 42 名 NPC 的种子世界、修炼与关系、宗门与战斗等规则流程，以及事件记录、章节生成、玩家确认和导出。模型生成失败时使用规则摘要，向量索引异常时可从事件账本重建。

它验证了规则系统与生成式叙事可以共享同一产品流程。尚未验证的是数百小时游戏中的因果稳定性、内容平衡、玩家留存、语音体验和存档迁移，因此不能宣称已达到正式游戏发行质量。

15. 项目复盘与下一步

模型可能写出流畅章节，却遗漏敌人或写错境界，因此我将关键事实检查放在生成之后，并设置一次定向重写与规则摘要回退。SQLite 保留权威状态，向量检索仅用于查找旧事件，避免生成文本反过来改变既有游戏事实。

下一阶段先连续试玩，记录事实遗漏、人工修改和摘要回退原因，补充存档恢复测试，再评估长期玩法。
