1. 项目概览与核心价值

针对 AI 协作中需求未明确就开始实施、缺少验证就宣布完成的问题，我设计了 FDE Builder 本地项目推进工具，将澄清、批准、规划、执行、验证、汇报和完成组织为七阶段流程。

关键文档写入前先生成预览并由用户确认，写入时再次核对内容；若预览后信息变化，则拒绝旧预览。已批准阶段限制核心事实修改，任务、证据和报告按阶段关联。

2. 项目背景和机会判断

AI 编程工具很擅长快速生成方案和代码，但也容易在需求不清时直接开工，把模型猜测写成事实，或在缺少验证证据时宣布完成。对于 FDE 项目，这类过程问题会直接影响范围、成本和客户信任。

我把首版问题收敛为：在进入下一阶段前，检查需求是否明确、计划是否获批、完成结论是否有证据。工具通过可执行的状态规则提示缺失信息，项目判断仍由用户负责。

3. 目标用户、使用场景与现有流程

首位使用者是我本人，用于整理个人 AI 项目的需求、计划与验证资料；多人实施和客户交付仍是后续使用假设。

典型流程从一句模糊需求开始。用户经常需要在聊天记录、任务列表、测试结果和报告之间手动同步，项目中途也很难判断哪些内容已确认、哪些只是模型假设。FDE Builder 将这些材料放入同一项目状态和证据链中。

4. 需求与优先级

P0 是需求未达到最低完整度时不能进入实施。

P0 是模型候选答案标为待确认假设，不能替用户确认事实。

P0 是阶段跃迁、关键写入和完成结论需要人工批准。

P0 是验证结论能够追溯到不可静默替换的证据。

P1 是中断后可以恢复，并只显示当前最需要完成的一项动作。

P2 是团队协同、远程权限和外部项目管理系统集成。

5. 目标与验收标准

首版成功标准包括：

负责人、期望结果、首版交付、期限和下一步决策等五项核心字段满足要求后，才生成简报预览；

计划、验证和汇报均生成可审阅预览；

预览后、写入前信息发生变化时，旧预览不能继续提交；

所有必要任务、证据和报告门禁满足后才能完成；

证据副本保留 SHA-256 摘要；

审计可以发现非法阶段、孤立任务、证据损坏和文档状态不一致。

业务结果不以“完成了多少代码”衡量，而以是否能够形成明确的继续、调整或停止决策衡量。

6. 我的职责与协作边界

我设计七阶段流程和五项澄清字段，区分内容确认与阶段批准；重点验收预览后、写入前信息变化时阻止提交旧预览，以及阶段批准后的核心事实锁定和证据一致性检查。

这是个人项目治理原型，没有真实客户交付数据。可选本地模型只生成候选答案或假设，不具备批准项目、确认事实或宣布完成的权限。

7. 调研、替代方案与范围取舍

我参考了 Discovery、Alpha 和软件安全开发的阶段思路，并比较了文档模板、通用任务管理软件和自由对话 Agent。

我选择状态机与命令式交互：程序记录项目当前阶段，每次操作先检查这一阶段允许的动作，以及推进所需的确认和证据。文档模板用于表达需求与计划，状态规则负责在信息或证据缺失时阻止继续，使流程要求能够实际执行。

首版使用本地文件和 Python 标准库，集中验证流程治理，暂缓 Web 协作和第三方系统集成。

8. 方案与使用流程

用户创建项目后，系统围绕负责人、期望结果、首版交付、期限和下一步决策补齐信息，一次展示当前需要回答的问题。

五项核心信息确认后，系统生成简报预览。用户先确认内容并写入简报，再决定是否批准进入规划；随后生成计划与任务。执行过程中记录任务状态和证据。

验证阶段汇总测试与证据，用户审阅验证报告；汇报阶段形成结果、风险和决策建议。只有所有门禁通过后，项目才能完成。任何阶段都可以通过 status 查看当前状态，并通过 resume 从中断点继续。

9. 三项关键决策及其权衡

第一，采用固定七阶段状态机。流程更可预测、可审计，也会限制用户随意跳步。对需要证据的实施项目，这种约束具有实际价值。

第二，关键写入采用“预览、确认、提交”。系统记录预览内容的指纹；预览后、写入前信息变化时，拒绝提交旧预览，要求重新生成并确认，避免确认内容与实际写入内容不一致。

第三，将证据复制进项目，并记录 SHA-256 内容摘要。复查时重新计算摘要并与原记录比较，可以发现文件是否发生变化；证据能否支持任务结论，再由人审阅判断。这样保留了可检查的材料副本，代价是增加存储占用和证据维护工作。

10. AI、规则与人工分工

可选本地模型为当前问题提供候选答案，并保存为待确认假设；它不直接生成已批准的最终文档，也不能推进阶段。

规则引擎决定当前阶段、允许命令、门禁是否满足、预览是否过期和证据是否完整。文件工具负责原子写入、追加事件和生成哈希。人工负责确认需求、批准计划、判断验证结果，并做出继续、调整或停止决策。

11. 数据与技术方案

每个项目包含 initiative.json、追加式 events.jsonl、项目简报、计划、任务、验证报告、最终报告和证据账本。写入采用临时文件替换，降低中断造成半写状态的风险。

证据来源被限制在允许目录，复制后保存文件名、大小、内部标识和 SHA-256，不在项目记录中保存机器相关的完整源路径。可选 Ollama 地址只允许本机回环地址。

12. 评测与案例复盘

自动化测试覆盖阶段跃迁、未完成澄清、非法命令、预览过期、乱码输入、重复写入、证据路径、哈希变化和审计异常。

预览过期测试中，系统先生成简报预览，再在写入前修改期限；提交旧预览时被拒绝，并要求重新预览。该用例不代表系统已支持在计划批准后随意修改项目目标。

另一个案例是证据文件复制后被替换。审计会重新计算哈希并报告不一致，阻止系统把该证据用于完成结论。对于乱码或明显损坏的输入，系统停止处理，避免把不可读内容沉淀为正式项目事实。

13. 风险与异常处理

系统默认本地运行，不依赖云端密钥。证据路径经过规范化和目录边界校验，防止路径穿越；关键 JSON 和 Markdown 使用原子写入；事件日志采用追加方式保留历史。

本地模型不可用时仍可手动回答问题并推进允许的阶段。模型建议不会自动改变状态；已批准阶段的核心事实受锁定限制。多人角色、正式变更审批和组织级签名尚未实现。

14. 成果与验证范围

本阶段完成可恢复的七阶段项目流程，以及预览确认、任务证据和审计检查。自动化测试覆盖预览过期、非法阶段跳转与证据哈希变化；模型提供候选答案，阶段推进和完成判断由程序规则与人工确认控制。

尚未验证的是多人项目中的审批效率、复杂交付场景的适配性和长期证据维护成本。潜在价值是降低需求误解和无证据交付，但需要真实项目对照试点才能量化。

15. 项目复盘与下一步

简报预览与写入之间可能发生内容变化，我将二次核对纳入写入条件；批准后的核心事实则限制修改。证据文件变化时通过哈希检查提示异常，使“是否允许继续”有具体检查依据。

下一阶段先用一个低风险个人项目完整走通澄清、确认、执行和验收，记录哪些步骤必要、哪些提示难懂；再考虑正式变更流程和可配置阶段。
