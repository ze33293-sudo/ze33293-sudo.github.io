1. 项目概览与核心价值

在本地 RAG 原型基础上，我针对笔记更新后索引失效、旧版本混用和来源难追溯等问题，设计了基于 Obsidian 的知识检索与维护系统，加入增量同步、混合检索、权限过滤、重复内容确认和审计。

用户继续在 Obsidian 中维护 Markdown，系统同步文件变化并提供带引用的检索结果。产品重点是让知识更新、访问范围和异常处理进入日常流程，而不是只在固定文档上完成一次问答。

2. 项目背景和机会判断

个人笔记会修改、重命名和删除，也可能保留相近版本。因此我把关注点从一次问答扩展到索引更新、内容可见范围和重复确认，检查后续维护是否影响检索结果。

完成个人知识库的原理验证后，我将下一阶段范围扩展到文档修改、重命名、删除、过期和权限变化，优先检查索引能否同步、回答是否引用当前允许使用的内容。

3. 目标用户、使用场景与现有流程

首位使用者是我本人，知识源为个人 Obsidian 项目资料与学习笔记；多角色规则通过本地测试验证，尚未接入真实组织身份。

用户仍在 Obsidian 中撰写 Markdown，通过属性管理负责人、访问级别、复核周期、过期时间和索引开关。系统自动发现变更、更新索引，并提供带引用问答、文档健康检查、重复候选和审计状态。

4. 需求与优先级

P0 是 Obsidian 文件保持唯一事实源。

P0 是权限与过期过滤必须发生在内容进入模型上下文之前。

P0 是回答引用只能来自本次允许的检索结果。

P1 是新增、修改、重命名和删除可以增量同步，且不留下孤立索引。

P1 是重复内容由系统提示、人工确认，不能自动覆盖。

P1 是索引和备份可以校验、审计和重建。

P2 是多用户协作、组织目录和企业连接器。

5. 目标与验收标准

产品指标包括：

正向检索样例 Top 5 是否命中至少一个预期来源；

检索模式下对负向问题的正确拒答判定率；

检索引用路径是否存在、标题是否对应源文档；

通过独立边界测试检查受限、过期和已确认重复内容是否被排除；

索引修改、重命名和删除后无孤立记录；

审计链与备份清单可验证。

现存固定评测为 31 条样例，含 27 条正向和 4 条负向，均使用 search 模式、owner 角色并允许过期内容，关闭模型重排。记录中的 Top 5 来源命中率、检索模式负向拒答率和引用路径标题有效性均为 1.00，不代表生成回答或权限隔离效果。

6. 我的职责与协作边界

我制定笔记元数据和新增、修改、删除后的索引规则，将权限过滤放在检索前；选择人工确认重复内容、从 Markdown 重建索引，并分别记录检索结果与权限边界测试。

知识源来自个人 Obsidian 资料，没有真实企业租户或跨部门用户。系统验证的是治理机制和本地使用流程，尚未完成组织级身份与权限集成。

7. 调研、替代方案与范围取舍

我比较了单纯向量库、云端知识平台和本地 Markdown 事实源。单一向量库难以承担版本和内容维护；云平台使用方便，却会改变本地资料与权限边界。

最终保留 Obsidian Markdown 作为权威内容，SQLite 与向量只是可重建索引。检索采用全文与向量混合，而非只依赖语义相似度；重排仅在候选分歧较大时触发，减少不必要的本地推理。

8. 方案与使用流程

系统启动后先进行全量一致性检查，再监听文件变更，并每五分钟进行一次补偿扫描。Markdown 经过路径、Frontmatter、隐藏字符和潜在指令检查后，按 H1-H3 标题与段落切片。

普通内容按章节组织，长段落以约 800 字符为目标、1200 为上限、120 为重叠；表格和代码块保持完整。

查询进入系统后，先根据调用者角色、access、过期状态、索引开关和重复确认状态过滤可见文档，再分别执行 SQLite FTS5 与本地向量检索。两路结果通过 RRF 合并；仅当首批文档分数接近且来源分歧时，才调用重排模型。

最多五个切片、约八千字符进入语言模型。模型输出结构化答案，引用必须通过白名单验证；证据不足时拒答。

9. 三项关键决策及其权衡

第一，Obsidian Markdown 是唯一事实源。索引可以删除并重建，避免用户在数据库和笔记之间维护两份内容；代价是需要严格处理文件变化和元数据质量。

第二，在全文与向量检索前按角色和文档元数据过滤可见内容，限制进入候选和模型上下文的资料范围；代价是每次查询都需要明确角色。当前由本地边界用例检查过滤行为，组织身份集成与完整泄漏测试仍需补充。

第三，重复内容只生成候选，由人工确认 duplicate-of。这样避免相似文本被错误合并；代价是需要维护控制台和人工处理队列。

10. AI、规则与人工分工

Embedding 模型把文本转换为可比较的向量，帮助寻找措辞不同但含义相近的资料；全文检索补充明确的关键词匹配。需要重排时，再比较问题与候选内容的相关性，调整顺序。语言模型最后依据允许使用的片段组织答案。

程序先检查文件位置、笔记顶部属性和访问权限（ACL），过滤不应使用的内容，再限制送入模型的文本量，并核对引用是否属于本次检索结果。文件监听与一致性扫描负责同步笔记变化；人工维护内容、访问级别、复核周期，并确认哪些笔记确实重复。

11. 数据与技术方案

知识源为个人 Obsidian Markdown。元数据包含稳定 kb-id、owner、access、rag-index、review-cycle-days、next-review、expires 和 duplicate-of，用于索引、访问范围及维护提示。

SQLite 保存文档、切片、FTS5 索引、审计和指标；Ollama 生成 Embedding，并在需要时完成回答。启动配置强制本地模式，API 默认监听 127.0.0.1:8765。

普通查询与管理接口使用不同 Bearer Token，数据库只保存 Token 的 SHA-256。备份以 ZIP 和 SHA-256 清单交付，索引数据库可以从 Markdown 重建。

12. 评测与案例复盘

以下 31 条记录来自检索模式，不执行答案生成，模型重排也关闭；按 owner 角色查询且允许过期内容。记录结果为：

正向样例：27 条；

负向样例：4 条；

正向样例 Top 5 命中率：1.00（脚本字段名为 recall_at_5，判定为命中至少一个预期来源）；

检索模式负向样例拒答率：1.00，仅表示对这 4 条负向查询的拒答判定，不涉及模型生成回答。

引用路径与标题有效性：1.00（不衡量答案对引用的语义支持）；

另有 9 项自动化测试覆盖索引修改、重命名、删除、权限、过期、重复确认、伪造引用和审计。它们与上述 31 条检索样例是不同验证范围，不能合并为全场景正确率。

一个关键 Bad Case 是模型输出一个格式正确但不在本次检索白名单中的引用。系统会拒绝该答案并进入安全回退，防止模型伪造来源。

另一个案例是高度相似的两份笔记。系统只把它们标为重复候选；在人工确认前，两份内容仍保持独立。确认后，被标记文档才从默认检索中排除。

独立测试使用构造笔记检查公开角色的全文检索结果：排除私有与已确认重复内容，并对照是否包含过期资料。这些用例不等于答案、引用和审计摘要的完整泄漏测试。

13. 风险与异常处理

服务默认仅在本机监听。查询与管理使用独立 Token；路径规范化阻止目录穿越；隐藏目录、不可见字符和提示注入模式在入库时扫描；审计日志对邮箱、电话和密钥模式进行脱敏。

Ollama 不可用时，系统退回 FTS5 和带引用摘录，不使用模型记忆生成完整回答。ACL 校验失败时关闭请求，而非返回部分结果。索引损坏时从 Markdown 重建，备份通过哈希清单检查完整性。

14. 成果与验证范围

本阶段实现个人笔记的增量索引、混合检索、权限过滤、重复确认、引用约束和维护流程。31 条固定记录验证检索来源命中、检索模式负向拒答与引用路径标题，权限等机制另由自动化测试检查；生成回答质量仍需单独评测。

项目将原有 RAG 实验延伸到知识维护：新增、修改和删除需要同步，受限及过期内容需要过滤，相似笔记需要人工判断是否重复。当前验证基于个人 Obsidian 资料，组织身份集成、多用户并发和大规模语料仍在验证范围之外。

15. 项目复盘与下一步

格式正确的引用仍可能不属于本次检索结果，因此我增加引用白名单校验；相似笔记也可能包含不同信息，因此只提示重复候选，由人工确认。通过这些案例，维护与校验机制被落实到具体交互和测试中。

下一阶段先补生成模式的答案与引用支持评测，再加入不同角色及过期状态的对照，避免用 owner 检索结果代替权限验收；同时记录个人笔记更新后的同步和重复处理问题。
