1. 项目概览与核心价值

项目版本与基本信息

项目定位：整合对话、工具执行与任务状态的本地 AI 工作台

项目版本：0.1.0

项目形态：Windows 桌面应用、认证后的本地网页、CLI

项目角色：个人产品实践，负责产品设计与验收，使用 AI 编程工具辅助实现

当前阶段：Windows 0.1.0 安装包已生成，15 项聚焦回归测试通过

基于个人 AI 实践中频繁切换聊天、终端和文件工具的经历，我设计了 NekoFlow 本地 AI 工作台，将任务执行、文件操作、人工介入和状态展示整合到统一入口。首版先验证安装配置与本地认证，任务完成、取消和中断恢复另作专项验收。

工作台、配置、会话与主要数据保存在用户电脑。用户可选择本地或云端模型，推理是否离线取决于所选服务。项目以减少上下文搬运和工具切换为目标，实际改善程度仍需通过任务测试验证。

2. 项目背景和机会判断

在个人 AI 应用实践中，我需要频繁切换聊天窗口、终端、文件管理器、浏览器和笔记工具。上下文分散后，AI 很难持续理解任务状态，用户也难以判断模型执行到了哪一步、修改了哪些内容以及失败后如何继续。

我将首版重点放在任务状态和用户控制上：让用户知道任务执行到了哪一步、工具可以访问什么，以及失败后如何继续。产品方向参考了 Local-first Software 对数据控制权与本地使用的讨论，具体取舍以个人实践和首版验收要求为依据。

3. 目标用户、使用场景与现有流程

首期以我本人的 AI 项目实践为使用场景，潜在用户是同样需要同时处理模型、代码和文件的个人开发者及 AI 学习者。

首版聚焦个人项目中的文件与任务操作：用户提出目标，查看执行状态，在需要时授权或介入，再检查输出结果。多阶段研究、长期记忆和中断恢复属于扩展场景，其完整体验需要另行验收。

当前需求判断依据个人实践与竞品拆解，其他用户是否存在同样需求仍待验证。

4. 需求与优先级

我先解决安装、授权和失败提示，因为这些条件不成立，就无法可靠地验收后续任务体验。

P0：用户能够安装并启动应用，明确授权访问范围，并在访问被拒绝或配置出错时得到提示。

P1：围绕一项实际任务检查执行状态、人工介入、结果查看，以及取消和恢复过程。

P2：在核心任务流程通过验收后，再扩展工具入口、模型服务和其他操作系统。

长任务稳定性和其他用户的使用体验仍需专项验证。

5. 目标与验收标准

以下是安装交付与基础运行的验收要求；现有聚焦测试覆盖情况见本章末尾及评测章节。

形成无需用户另装 Python、Node.js 的 Windows 安装包；

桌面端提供完整能力，本地网页覆盖核心工作台，并明确提示桌面专属功能；

配置、文件、终端和 WebSocket 接口均经过本地会话认证；

分别检查应用数据保存位置、服务端口和模型并发限制是否符合配置；涉及 Docker 的执行隔离另用实际工具任务验收。

品牌版本、安装配置、本地认证及运行配置的聚焦回归检查通过。

已生成 NekoFlow 0.1.0 Windows 安装包，约 500MB；历史记录中 15 项聚焦回归测试通过，主要检查配置契约和本地认证，不等同于干净环境安装或全功能验收。

6. 我的职责与协作边界

我比较网页、CLI 与桌面方案，确定首版范围与验收标准：桌面端承载本机工具能力，本地网页提供核心入口。使用 AI 编程工具辅助实现，负责问题复现、测试检查与版本验收。

我将需求拆成认证、隔离、打包、模型管理和界面整合等可验证任务，使用 AI 编程工具辅助实现和排错，并负责源码检查、问题复现、测试设计与验收。上述职责来自个人实践，不包含客户交付或企业运营。

7. 调研、替代方案与范围取舍

我评估了三种形态：

纯网页方案分发方便，但本地文件、终端和系统能力受限；

CLI 方案灵活直接，但学习门槛较高，任务状态不易观察；

桌面外壳加本地服务可以兼顾图形体验和本机工具能力，同时保留网页与 CLI 入口。

最终选择 Electron 桌面端作为完整产品载体，以本地 FastAPI 服务统一能力，并将 Web 定义为经过认证的核心功能入口。首版优先完成 Windows 交付；macOS、Linux 和大规模协作暂不进入验收范围。

8. 方案与使用流程

产品流程设计为：安装并配置模型后进入聊天或任务空间，围绕目标组织步骤，在权限范围内调用本机工具，并保留状态与结果。复杂任务可进一步涉及条件路由、人工介入和检查点；当前聚焦回归记录主要覆盖安装配置、认证与运行配置，真实任务的完成、取消和恢复仍待专项验收。

桌面端承载目录选择、内置浏览器和系统控制等原生能力；网页端覆盖聊天、任务、记忆、编辑器、市场和配置，并对不可用能力给出明确去向。这一设计参考了 Google PAIR（https://pair.withgoogle.com/guidebook-v2/chapters） 对用户控制、反馈和优雅失败的建议。

9. 三项关键决策及其权衡

决策一：桌面端承担完整体验。

桌面外壳便于接入本机文件、终端和浏览器，但增加了打包体积与跨平台维护工作。首版保留认证后的网页入口，桌面专属能力通过界面说明区分。

决策二：localhost 仍然需要认证。

NekoFlow 使用一次性入口建立本地会话，使用后轮换令牌；未认证的受保护 API 返回 401，认证跳转限制为回环地址。这个设计用于限制未授权访问，相关用例纳入测试，但不代表已完成全面安全审计。

决策三：模型能力与执行边界分离。

主模型、任务模型和视觉模型分别配置，请求频率、并发数及上下文上限由程序设置。工具提供可选 Docker 执行路径，实际执行范围仍取决于宿主权限和配置，不能仅凭存在沙盒入口认定所有操作已隔离。

10. AI、规则与人工分工

参与方主要职责
AI理解目标、生成计划、整理上下文、提出工具调用和输出候选结果
确定性规则鉴权、权限检查、模型限流、端口选择、状态保存和错误返回
工具层执行文件、终端、浏览器、检索及沙盒操作
用户配置模型、授予权限、介入关键节点、终止异常任务并验收结果

这套分工遵循 Microsoft 人机交互指南（https://www.microsoft.com/en-us/research/project/guidelines-for-human-ai-interaction/）提出的能力说明、便捷纠正和全局控制原则。

11. 数据与技术方案

产品由 Electron 桌面层、React/Vite 界面、本地 FastAPI 服务和 Python Agent 运行层组成。模型通过 OpenAI 兼容协议接入，可使用 Ollama 本地模型或用户配置的远程服务。

会话、配置、记忆、扩展和认证状态集中保存在 ~/.nekoflow。记忆层支持混合检索、语义关系和知识图谱；Docker 为隔离执行的可选依赖。Docker 不可用时，聊天仍可启动，依赖沙盒的工具会明确不可用。

12. 评测与案例复盘

项目保留 15 项聚焦回归测试：9 项检查品牌、版本、安装配置和启动契约，3 项检查本地认证，3 项检查运行配置与模型限制。这些配置断言不等同于真实容器隔离测试。

2026 年 9 月 9 日复测结果为 15/15 通过，耗时约 2 秒。同时记录到一条测试依赖弃用警告，当前不影响结果，但需要在后续依赖升级中处理。

重点失败模式包括：

一次性入口被重复使用时必须拒绝；

认证跳转指向外部网站时必须回落到本地地址；

未认证请求访问私有 API 时必须返回 401；

模型并发配置变化后必须替换旧信号量，避免旧限制继续生效。

该测试集属于聚焦回归验证，尚未覆盖完整 UI 自动化、长任务压力、崩溃恢复和多平台安装。

13. 风险与异常处理

应用 API 和 Docker 映射端口只绑定 127.0.0.1；会话使用 HttpOnly、SameSite=Strict Cookie；配置响应隐藏模型和扩展凭据；界面与 Agent 文件操作共用权限策略。Electron 窗口启用 contextIsolation 并关闭 nodeIntegration，符合 Electron 安全建议（https://www.electronjs.org/docs/latest/tutorial/security）。

当前 Cookie 服务于本机 HTTP，因此没有启用 Secure 属性。若未来开放局域网或远程访问，需要升级为 HTTPS，并补充 Origin、CSRF 和更严格的会话保护。OWASP 会话管理指南（https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html）也将 HttpOnly、SameSite 和 Secure 视为组合防护。

本地优先无法消除所有风险：使用云模型时，提交内容仍受外部服务条款约束；安装的扩展可能运行第三方代码；用户仍需负责本地备份。风险划分参考了 NIST AI RMF（https://www.nist.gov/publications/artificial-intelligence-risk-management-framework-ai-rmf-10）对可靠性、安全、透明度和隐私的要求。

14. 成果与验证范围

本阶段生成 Windows 0.1.0 安装包，并完成桌面与网页功能划分、认证及运行配置的实现与说明。2026 年 9 月 9 日记录的 15 项聚焦测试通过；完整 UI、真实任务恢复、长任务和干净环境安装仍待专项验收。

后续将用任务完成率、人工介入次数和中断恢复情况验证产品体验。当前尚未测量工具切换时间、用户留存或付费情况，效率改善仍作为试用阶段的验证目标。

15. 项目复盘与下一步

首版优先处理安装、认证和运行隔离，使后续任务体验测试具备可运行的基础。例如，一次性入口复用、外部认证跳转和旧并发限制残留都被纳入回归检查。下一轮验收应转向实际 Agent 任务的完成、取消和恢复过程。

下一阶段先在干净 Windows 环境检查安装和首次启动，再选择一项文件任务，记录执行、取消、失败提示与恢复结果。完成核心路径验收后，再考虑长任务测试、代码签名和其他平台构建。
